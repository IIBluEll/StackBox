# StackBox 개발 구조

> 문서 버전: v0.1 / 2026-10-02  
> 범위: 싱글 플레이 개발 구조. 멀티 모드는 보류한다.  
> 상태: 논의로 합의한 설계 기준이며, 구현과 실행 검증은 아직 수행하지 않았다.

## 1. 설계 방향

게임을 설정값, 규칙 계산, 한 판의 진행, Unity 오브젝트, UI로 구분한다.

- 설정값은 ScriptableObject에 모아 플레이 테스트 중 쉽게 조정한다.
- 속도, 배치 판정, 보상 계산은 일반 C# 클래스에서 처리한다.
- 블록 이동, 생성, 크기 변경, 조각 낙하와 연출은 Unity 컴포넌트가 담당한다.
- 한 판의 진행 순서와 계산 결과 적용은 `StackGameProvider`가 담당한다.
- UI에만 HM.Codebase 기반 MVP를 적용한다.
- Combo와 Fever는 처음부터 별도 Controller로 나누지 않고 `StackRunRule`에서 함께 계산한다. 책임이 복잡해졌을 때 분리한다.

일반 C# 분리의 주된 목적은 책임을 명확하게 하고 계산을 독립적으로 검증하기 쉽게 만드는 것이다. 분리 자체가 성능 향상을 보장하지는 않는다. 성능은 실제 Transform 접근, 메모리 할당, 오브젝트 수와 실행 측정으로 판단한다.

## 2. 구성과 책임

| 구성 | 형태 | 책임 |
|---|---|---|
| `StackGameConfig` | ScriptableObject | 속도, 판정 범위, 회복 조건과 회복량, 점수 등 설정값 보관 |
| `StackRunState` | 일반 C# 데이터 | 현재 판의 게임 상태, 점수, 성공 배치 수, Combo, Gauge, Fever와 결과 통계 보관 |
| `StackPlacementRule` | 일반 C# 계산 클래스 | 겹침, Perfect / Normal / Miss, 남는 영역, 잘리는 영역, 절단 전 보너스 수집 여부 계산 |
| `StackRunRule` | 일반 C# 계산 클래스 | 배치 결과에 따른 점수, Combo, 회복, Gauge, Fever와 다음 블록 속도 계산 |
| `StackGameProvider` | 진행 담당 Unity 컴포넌트 | 시작, 입력 수락, 계산 호출, 결과 적용, Pause, Game Over, Retry, Home과 비동기 작업 수명 관리 |
| `StackInputController` | Unity 컴포넌트 | 장치 입력 통합, UI 입력 제외, 중복 입력과 메뉴 입력 재사용 차단 |
| `StackBlockSpawner` / `StackBlock` | Unity 컴포넌트 | 블록 생성, 위치와 크기 적용, 오브젝트 정리 |
| `StackBlockMover` | Unity 컴포넌트 | 생성 시 정해진 축, 범위, 속도로 매 프레임 왕복 이동 |
| `StackBlockCutter` | Unity 컴포넌트 | 계산 결과를 남은 블록에 적용하고 잘린 조각을 생성해 낙하시킴 |
| 카메라 / 환경 / 효과 컴포넌트 | Unity 컴포넌트 | 확정된 결과에 따른 추적, 색상, Biome, 시각 효과와 Audio 표현 |
| HUD / Result MVP | UI 구성 | 게임에서 확정된 데이터 표시와 사용자 버튼 입력 전달 |
| 저장 담당 구성 | 저장 경계 | 최고 기록과 설정 유지, 정해진 시점에 영구 저장 |

표는 책임의 경계이며 모든 구성을 동시에 구현해야 한다는 뜻은 아니다. 작은 기능은 기존 담당 구성 안에서 시작하고, 독립적인 책임이 생기면 분리한다. Provider는 각 계산과 표현을 호출하고 순서를 조율하며, 계산식과 개별 연출 구현을 직접 떠안지 않는다.

기존 [게임 기획서](Stack_Game_Design_Document.md)의 21절에 있는 Combo / Fever Controller 목록은 기능별 책임을 나타낸다. 이번 합의에서는 초기 계산을 `StackRunRule`로 묶고, 필요한 시점에 분리하는 방식을 개발 기준으로 사용한다. 게임 규칙과 수치는 기존 기획서를 따른다.

## 3. 데이터 경계

| 데이터 | 내용 | 사용 기준 |
|---|---|---|
| `StackGameConfig` | 기본·최대 속도, 속도 증가량, Perfect 범위, 회복 간격·회복량, 점수, Gauge와 Fever 설정 | 설정값이며 실행 중인 판의 점수나 Combo를 저장하지 않음 |
| `StackRunState` | 게임 상태, Score, 성공 배치 수, 현재·최대 Combo, Gauge, Fever 남은 횟수·발동 횟수, 최고 도달 환경 등 | 현재 판 상태의 원본. Provider의 처리 경로에서만 변경 |
| `StackBlockData` | 위치, 크기, 이동 축 | 계산에 전달하는 블록 정보. Transform을 계산 클래스에 직접 전달하지 않음 |
| `StackPlacementResult` | 판정, 이전 크기, 남는 영역, 잘리는 영역, 보너스 수집 여부 | 절단·Snap·회복을 적용하기 전 위치로 계산한 판정 결과 |
| `StackTurnResult` | 갱신할 판 상태, 회복 후 최상단 블록 정보, 발생한 보상과 상태 전환 | 한 번의 배치로 적용할 최종 결과 |

클래스와 구조체 중 어떤 형태로 선언할지, 구체적인 필드와 함수 시그니처는 구현 시 결정한다.

`StackBlockData`는 계산을 위한 값 묶음이다. 움직이는 블록의 위치는 입력 수락 시 Unity 컴포넌트에서 확정해 전달하고, 서로 다른 위치 원본을 따로 갱신하는 구조를 만들지 않는다. `Vector3` 같은 값 타입을 계산에 사용하는 것은 허용한다.

UI Model은 표시할 확정 데이터만 가진다. `StackRunState`를 대신 소유하거나 점수, Combo, Gauge를 변경하지 않는다. UI와 연출에 전달하는 데이터는 해당 배치가 끝났을 때의 값이 유지되도록 구성한다.

## 4. 설정값과 게임 규칙

| 설정값 | 일반 C#에서 계산할 규칙 |
|---|---|
| 기본 속도, 최대 속도, 속도 증가량 | 성공 배치 수로 다음 블록의 이동 속도 결정 |
| Perfect 기본 범위, 크기 대비 범위 상한 | 이전·현재 블록의 위치와 크기로 판정 결정 |
| 회복 Combo 간격, 회복량, 최대 크기 | 해당 Combo에 도달하면 최대 크기를 넘지 않도록 회복 |
| 일반 점수, Fever 점수 | 배치 당시 Fever 상태로 점수 결정 |
| Gauge 충전량, Fever 진입값, 지속 배치 수 | 충전, 다음 블록부터의 진입, 마지막 보너스 배치와 종료 결정 |

설정값은 최종 밸런스로 확정한 수치가 아니다. 플레이 테스트를 통해 조정한다.

현재 기획에서 Combo는 회복 조건에 영향을 주며 직접 추가 점수를 주지 않는다. 성공 배치는 일반 상태에서 +1, Fever 중에는 +2를 받는다.

다음 블록의 속도와 왕복 범위는 생성 시 확정한다. Unity 컴포넌트가 그 값으로 매 프레임 이동하며, 한 블록이 이동하는 동안 속도와 범위를 임의로 바꾸지 않는다.

## 5. 배치 한 번의 처리 순서

1. Provider가 `PLAYING` 상태인지, 이동 블록이 준비되어 있는지, 입력을 받을 수 있는지 확인한다.
2. 입력을 수락하면 즉시 추가 배치 입력을 잠그고 이동을 멈춘다. 이전 블록과 현재 블록의 위치·크기를 확정한다.
3. `StackPlacementRule`에 값을 전달해 판정, 남는 영역, 잘리는 영역과 보너스 수집 여부를 계산한다. 보너스 수집은 Snap과 절단 전 좌표를 사용한다.
4. `StackRunRule`이 현재 판 상태와 판정 결과로 다음 상태와 보상을 계산한다.
5. Provider가 계산 결과를 판 상태와 실제 블록에 적용한다. 성공이면 Snap 또는 절단과 필요한 회복을 적용하고, Miss면 현재 블록 전체를 낙하시킨다.
6. 모든 상태 적용이 끝난 뒤 UI와 연출에 확정된 결과를 전달한다.
7. 성공이면 UniTask로 짧은 준비 시간을 기다린다. 회복 후 최상단 크기를 상속한 다음 블록을 생성하고, 새 입력을 받을 수 있을 때 배치 잠금을 해제한다.
8. Miss면 다음 블록을 생성하지 않는다. Game Over 상태를 즉시 확정하고, 낙하 연출 대기 후 Result 화면을 표시한다.

보상 계산 내부 순서는 기획서 3절을 따른다.

- 배치 당시 이미 Fever였는지를 기준으로 점수를 계산한다.
- 성공 배치 수와 Combo를 갱신하고 해당하면 회복한다.
- 기존 Fever 배치였다면 남은 횟수를 줄이고 Gauge를 충전하지 않는다.
- Fever 밖의 배치였다면 판정과 보너스 수집 여부에 따라 Gauge를 갱신한다.
- Gauge가 진입값에 도달하면 다음 블록부터 Fever를 적용한다.
- 갱신된 성공 배치 수로 다음 블록의 속도와 환경을 결정한다.
- Miss에는 성공 점수, 회복, Gauge 충전을 지급하지 않는다.

## 6. 상태 변경과 이벤트

규칙 클래스는 입력 상태를 직접 변경하지 않고 계산 결과를 반환한다. Provider가 그 결과를 현재 판에 적용한다.

이벤트는 계산이 끝난 결과를 UI와 연출에 알리는 용도로 사용한다. 이벤트 구독 순서로 점수, Combo, 회복, Fever의 처리 순서를 결정하지 않는다.

`GAME_STATE`는 `READY`, `PLAYING`, `PAUSED`, `GAME_OVER`로 구분한다. Fever는 게임 상태와 별도로 유지한다. 배치 처리 중 여부도 별도로 관리하므로 `PLAYING`이어도 준비 대기 중에는 배치 입력을 받지 않는다.

같은 프레임의 여러 장치 입력은 현재 블록에 한 번만 적용한다. 시작, Retry, 재개에 사용한 입력은 새 블록 배치로 재사용하지 않으며, 해당 입력이 해제된 뒤 새 입력을 받는다.

## 7. UI MVP

- View는 `HM.CodeBase.AView`를 기반으로 텍스트, Gauge, 버튼과 안내를 표시한다.
- Presenter는 `HM.CodeBase.APresenter`를 기반으로 게임의 확정 데이터를 Model에 반영하고 View를 갱신한다.
- HUD와 Result는 각각 Model, View, Presenter를 둔다.
- Retry / Home 버튼 입력은 Presenter가 게임 진행 담당자에게 전달한다.
- 이벤트를 구독했다면 Close / Dispose에서 해제한다. 화면을 반복해서 열거나 Retry해도 구독과 버튼 호출이 중복되지 않도록 한다.
- Title / Pause / Settings는 해당 화면을 구현할 때 같은 방식을 적용한다.

## 8. 수명과 비동기 작업

| 수명 | 대상 | 종료 시 처리 |
|---|---|---|
| 한 판 | 판 상태, 탑, 이동 블록, 조각, 보너스 표식과 방향 순서, 판의 비동기 작업 | Retry / Home / 씬 종료에서 이전 작업 취소와 오브젝트 정리 |
| UI 화면 | 이벤트 구독, 화면의 비동기 연출 | Close / Dispose에서 구독 해제와 연출 취소 |
| 플레이 사이 | 최고 기록, 사용자 설정 | Retry에서도 보존하고 정해진 시점에 영구 저장 |

UniTask는 다음 블록 준비 대기, Game Over 결과 표시 대기와 순차 연출에 사용한다. 배치 판정과 보상 계산은 즉시 처리하고, 매 프레임 이동도 Unity 갱신 루프에서 처리한다.

취소와 일시정지는 구분한다. Retry / Home에서는 이전 판의 작업을 취소하고, Pause에서는 이동·입력·준비 대기·연출의 진행을 멈춘 뒤 재개한다. 재개 후 이전 흐름은 한 번만 이어져야 한다.

이전 판의 작업이 나중에 다음 블록을 생성하거나 Result 화면을 여는 일이 없어야 한다. 풀을 도입한다면 파괴 시 취소뿐 아니라 반환 시 해당 활성화 기간의 작업도 취소한다. 실제 비동기 대기 함수에는 사용자 컨벤션에 따라 `_async` 접미사를 사용한다.

## 9. 구현 순서

| 순서 | 구현 단위 | 확인할 기준 |
|---|---|---|
| 1 | 입력 → 이동 → 판정 → 절단 → 다음 블록 → 실패·Retry | X/Z 교대, 경계 판정, 중복 입력 차단, 이전 판 오브젝트와 작업 정리 |
| 2 | 기본 점수, Combo 회복, Result MVP, 최고 기록 저장 | 회복 후 크기 상속, 보상 중복 방지, 결과 표시와 Retry 반복 |
| 3 | Fever와 HUD MVP | 진입 배치 점수, 다음 5회 보너스, 마지막 배치의 Gauge 미충전 |
| 4 | 보너스 표식 | 절단 전 수집 판정, 크기·Combo 희생과 Gauge 보상, 생성 조건과 방향 순서 |
| 5 | Pause / Home과 입력·수명 경계 보완, 환경과 연출 확장 | 준비 대기 중 Pause·Retry, 화면 구독 수명, 플랫폼별 동작 |

각 단계에 필요한 상태, 입력 차단과 취소 처리는 해당 기능과 함께 구현한다. 마지막 단계까지 미루지 않는다. 구분한 단계는 작업 순서이며 기존 기획서의 PC 입력 장치, 저장, Pause, 보너스 등 완성 범위를 축소하지 않는다.

기본 흐름을 먼저 검증한 뒤 다음 기능을 연결한다. Pool과 추가 Controller 분리는 실제 성능 측정과 책임의 복잡도를 근거로 결정한다.

## 10. 기존 프로토타입과 검증 범위

현재 `StackPrototypeController`는 입력, 이동, 판정, 생성, 회복과 효과음을 함께 처리한다. 본 개발에서는 이 책임을 위 경계에 따라 분리한다.

현재 프로토타입의 Perfect 크기 비율은 50%, 회복 간격은 2 Combo이며, 기획서의 초기값인 10%, 5 Combo와 다르다. 본 개발의 설정값은 기획서를 기준으로 옮긴 뒤 플레이 테스트로 조정한다. 이 문서 작성 과정에서 프로토타입 코드는 변경하지 않았다.

설계 문서, 정적 계산 확인, Unity 컴파일, Play Mode, 실제 기기와 출시 빌드 검증은 구분한다. 현재 문서는 설계 합의를 기록하며 동작이나 성능 검증의 증거가 아니다.
